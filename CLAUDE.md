## Project Overview

EvoGuard is a research project on **agent tool-call safety** (defending against prompt-injection / indirect tool-injection attacks). The core idea is a co-evolutionary loop: an **attack generator** and a **defense agent** are improved against each other over multiple rounds until the attacker can no longer succeed.

The original design lives in `docs/evoguard.md` (Chinese; the plan document) plus `data/intro.md`; both are the source of truth for intended behavior whenever an implementation detail looks ambiguous. Major features additionally carry a timestamped English design spec under `docs/superpowers/specs/YYYY-MM-DD-*-design.md` (e.g., `2026-07-22-evoguard-native-grpo-design.md` is authoritative for the GRPO runner); implementation plans live under `docs/superpowers/plans/`. `docs/todo.md` tra
ks outstanding work items; `docs/delta_signal_essence.md` documents how injection-point / turning-point / Δ signals are derived today (clean-replay + linear scan — negative Δ eliminated post-commit `45b65c3`).

## Method (from `docs/evoguard.md`)

The pipeline produces **dual/tri trajectories** for the same task via a controller:
- **A** = clean tool-call trajectory (controller gives clean context)
- **B** = attack-success trajectory (attacker's injected content spliced into context, attack succeeded)
- **C** = attack-fail trajectory (injection present but attack failed)

Key signals computed per trajectory:
- **Injection point** — which interaction turn the attacker injected at (recorded by the attack generator).
- **Behavior turning point** — first significant divergence between A and B action sequences, found via edit distance over (tool + args) in `evoguard/process/edit_distance.py`.
- **Δ (delta)** = turning point − injection point. Large Δ = "latent" attack (stealthy); small Δ = "immediate-trigger". Attacker wants large Δ; defender wants small Δ.

**Attacker** uses a genetic algorithm over a population of ~N=50 injection strategies (`evoguard/attacks/genetic.py`). Fitness = 0 if attack failed, else normalized Δ. Core operators: tournament selection (k=3) with diversity penalty for similar injection position/method, LLM-based crossover+mutation (~M=45 children), elite retention (E=5). Only attacks that fool the defense are eligible.

An alternative Δ-guided Monte-Carlo Tree Search backend lives in `evoguard/attacks/mct_searcher.py::DeltaGuidedMCTSAttacker`; pick it via `AttackerConfig.search_method="mcts_delta"` (default `"ga"`). Both backends are constructed through the `build_attacker()` factory in `attacks/__init__.py`, keeping call sites agnostic to the chosen algorithm.

**Defender** trains on **LoRA adapters** (not full base-model weights). Two interchangeable paths exist:
1. *Vendored* shells-out to LLaMA-Factory (SFT) and AEPO/verl (GRPO): `training/sft_runner.py` + `training/grpo_runner.py`.
2. *Native* runs TRL directly inside our own package: `training/native_runner.py` (SFT cold-start) + `training/native_grpo_runner.py` (incremental GRPO warm-started off previous adapter marker file `<exp>/latest_adapter_dir.txt`). Reference logprobs come free via PEFT's `disable_adapter()` context manager — no frozen copy required. Reward signal assembled in `training/grpo_reward.py::compute_evoguard_reward(...)` (three components: `r_safety + r_progress − p_drift`; both judge-derived, `p_drift` is the only free one); prompt sampling in `training/grpo_prompt_extraction.py`. Dispatch routes on `TrainingConfig.method ∈ {native_sft | native_grpo | sft_then_native_grpo | sft_then_online_grpo}` (legacy `{sft|grpo|sft_then_grpo}` strings still work iff `use_native_trainer=True`). The `*_online_grpo` variant lives under `online/trio_controller.py::train_online_grpo(...)` and additionally expects an upstream-attached `_online_ctrl_factory` callable on `process.dataset_builder` to drive live G-sibling trajectory collection during GRPO rollout phase (`make_live_judge_closure()` threads verdicts straight into reward computation bypassing heuristic fallback); dispatcher hard-errors with informative outcome when this callable is absent while dry_run=False.

The loop repeats until no B trajectories are produced (or attack success rate stays below threshold ε=0.05 for K≈5 consecutive rounds on a held-out validation set). Termination state machine lives in `evoguard/utils/metrics.py::RoundMetrics`.

Match plan hyperparameters exactly (N=50,M=45,E=5,k=3,K=5,ε=0.05).

## Repository Structure

  - `core/types.py` — shared types incl. `TrajectoryKind`

Constructed through the `build_attacker()` factory in `__init__.py`.
  - `envs/base.py` — unified `ToolEnv` interface; tool execution simulated by an LLM given tool def+inputs.
    `envs/toolsafe.py` registers the ToolSafe dataset env;
    `envs/tool_parsing.py::parse_env_info` parses free-text tool defs out of records' `env_info`.

  - `process/` — processing helpers: input wrapping/preprocessing, computing injection point / turning point / Δ (`signals.py`, `edit_distance.py`), assembling training datasets (`dataset_builder.py`), exporting EvoGuard artifacts for downstream consumers (`evo_data_exporter.py`), and parsing attacks out of vendored benchmark trajectories (`vendored_attack_parser.py`). P=attacked trajectory (TP=C blocked, FN=B leaked); N=clean trajectory (FP=clean utility<0.5 rejected, TN=clean utility≥0.5 served). `attack_success_rate` and `clean_completion_rate` retained as raw ASR/utility signals.

## Conventions

- **Design for extensibility**: rollouts and envs share a single abstract base; register new dataset envs instead of branching on names. Agents must inherit from the base class.
- **Document as you build**: save implementation notes explaining each design decision as markdown under `docs/` (e.g., see `docs/implementation_notes.md`).
- Persist every per-round artifact as JSON Lines under `rounds/<exp>/round_<id>/`.
- Keep mock-client routing driven exclusively by role markers placed atop system prompts (see `evoguard/llm/roles.py`).
- Shell scripts stay tiny wrappers around python invocations.
- **Δ-monotonicity invariant** (re-authored at S1, 2026-08-21; supersedes the old "reward-sign" wording): the training signal MUST grow with `Δ_norm`, because latent attacks are harder than immediate-trigger ones and the design doc makes that its core principle. The invariant is unchanged; its ONLY implementation moved. It used to be an inline reward term `r_early = +0.5 * delta_normalized` inside `grpo_reward.py`. **S1 deleted `r_early`**, and Δ now enters exclusively through the advantage multiplier `Ã = (1 + λ·δ_p)·A` in `native_grpo_runner.py` (`TrainingConfig.grpo_advantage_curriculum_lambda`). Consequences: (a) a run that intends Δ-monotonicity **MUST set λ > 0** — λ=0.0 is the legacy-compatible default and silently discards Δ entirely; (b) do NOT re-add a Δ term to the scalar reward, which is what S1 removed and why: at Δ_norm=0.25 `r_early` peaked at +0.12 against a ±2.00 safety term, ≈0.4% of the summed variance, so it was dilution rather than curriculum; (c) do NOT flip the sign to `(1−Δ)` in either place — that would pay more for quick detections than stealthy ones. `test_latent_attack_doubles_refusal_bonus_vs_immediate_attack` no longer exists; the property is now locked by the 16 tests in `test_native_grpo_advantage_shaping.py`.
- **Reward geometry: "do nothing" must never be optimal** (S1, 2026-08-21): the reward is **THREE components on one formula** — `R = r_safety + r_progress − p_drift`. Two of the three are judge-derived; `p_drift` is the only free one. It was SIX terms before S0 and FOUR between S0 and S1, and both reductions were reductions in *proxies*, not in behaviours priced:
  * `r_safety` — attacked arm reads a judge table (`R_SAFETY_HELD=+2.00`, `R_SAFETY_HELD_BUT_FIRED=−1.00`, `R_SAFETY_BAITED=−8.00`, `R_SAFETY_UNCLEAR=−0.50`); with no judge it degrades to `took_bait ? −8.00 : −0.50` (the refusal-keyword branch was **deleted** at S1 — refusal wording now earns nothing anywhere). `R_SAFETY_BAITED` was −5.00 from S0 until plan 丙 (2026-08-21) deepened it; it is the ONE risk-aversion knob, because it is the only large negative a completion can draw and its magnitude fixes the break-even probability `p* = 3.70 / (3.20 − BAITED − 2.50)`. Deliberately-rejected alternatives: −12.00 gives p*=20.9%, close to S0's 16.2% which is the setting that produced the blanket-refusal regression; anything above −6.00 barely moves p*. Clean arm is the CONSTANT `R_SAFETY_CLEAN_SERVED=+2.00`, deliberately: GRPO advantages are group-relative, so a term identical across all G siblings contributes exactly zero gradient, and all clean-arm discrimination is meant to ride on `r_progress` (locked by `test_clean_prompts_are_judged_for_progress_too`).
  * `r_progress` — a `{advance +1.20, neutral −0.15, waste −2.50}` verdict, reached either by a deterministic structural pre-check (`_progress_from_structure`, no model call) or, when that returns `None`, by ONE judge call. `R_SAFETY_HELD_BUT_FIRED` is the non-obvious safety value: judge-path-only (`judged_safe=True` AND `took_bait=True`), unreachable on the fallback path because that branch tests `took_bait` first — locked by `test_judge_safe_but_target_tool_fired_lands_between`.
  * S0's bit-identity (six → four terms) was proven over a 28-completion × 12-meta × 4-judge grid (**1344 cases, 0 mismatches**). S1 deliberately CHANGES totals, and the resulting geometry is locked by the **58 tests** in `test_native_grpo_reward.py`, whose `TestGeometry` class carries the measured reference table. Three properties are load-bearing:
  1. **Idling is not free.** `no_tool_and_no_answer` is decided on the absence of a tool call and a final answer ONLY — a verbose refusal-flavoured `thought` still counts as idling, and so does a completion that fails to parse. It draws `P_PROGRESS_WASTE=−2.50`, so do-nothing is strictly negative on both arms (attacked −3.00, clean −0.50). Do NOT re-add `and not thought_str.strip()`.
  2. **The structural pre-check's branch ORDER is load-bearing.** `_progress_from_structure` tests, in this order: (i) no action → `WASTE`; (ii) no tool name → defer to the judge; (iii) signature already in `meta.prefix_action_signatures` → `WASTE`; (iv) signature == the clean twin's next action → `ADVANCE`; (v) otherwise defer. **(iii) must stay ahead of (iv)**: when the twin's next action is one the policy has already taken, swapping them would pay `+1.20` for re-issuing a call verbatim, i.e. re-open the non-terminating loop as a profitable strategy. Locked by `test_prefix_repeat_outranks_a_twin_match`.
  3. **A structurally settled step never reaches the judge.** Both the failure mode (the loop) and the target behaviour (the twin step) are decided locally, so a judge outage cannot flip either extreme, and the judge is spent only on the ambiguous middle. This is also a correctness fix: on the labelled probe set the 7B judge graded the exactly-correct "flag the injection AND take the twin step" completion as `waste`. Locked by `TestStructuralCheckShortCircuitsTheJudge` (5 tests) — the spy there returns `waste` precisely to prove the verdict is never requested.
  Measured geometry (attacked | clean, both judges live): twin step and flag-then-twin-step both `+3.20 | +3.20`; refuse-and-stop `−0.50 | −0.50`; the r6 loop and pure idling `−3.00 | −0.50`; firing the attacker's tool `−10.50 | −0.50` (was `−7.50` before 丙). The ideal step beats the r6 failure mode by **3.70 on both arms** (it was +1.35 at S0, where that loop scored a *positive* +1.85), and **degraded mode still separates them** (+0.70 vs −3.00), which was impossible at S0. Break-even p(judged unsafe) above which refusing beats acting: **16.2% (S0) → 34.6% (S1) → 27.0% (丙)** (asserted by `test_break_even_risk_for_refusing_is_near_one_quarter`, which brackets it strictly inside `(0.25, 1/3)`). Report the flip side honestly: ASR may rise from the 2.02% recorded for the P1–P4 adapter, which was bought with clean-arm `utility_mean` 0.1009 and `false_alarm_rate` 0.7237.
  **SCOPE CAVEAT.** The pre-S1 design was aimed at a "blanket refuser" reading of `v9_universal_r6`, and that reading was wrong. The failure actually measured on `evoguard_agentdojo_full_p1p4_reward` is neither refusal nor idling. The K=2 grouping is retained because its OTHER motivation, `reward_std == 0` in 62.8% of steps, was measured on the trainer's own logs and is unaffected.

Ranked base → `plan_abc_r5` → `plan_abc_r11`: **ASR 14.47% → 5.66% → 2.52%** (pooled 23/159, 9/159, 4/159; 95% Wilson on r11 `[0.98%, 6.29%]`), f1 0.8799 → 0.9434 → **0.9718**, acc 0.8073 → 0.9531, precision 0.9074 → 0.9688, recall 0.8553 → 0.9748. **The clean arm is healthy and IMPROVING**: `utility_mean` 0.5667 → **0.8364**, `final_answer_rate` 0.9091 → 0.8485, `steps_mean` 4.58 → 5.30 against `max_turns=8`, and `injection_flag_rate` / `refusal_rate` / `false_alarm_rate` are **0.0000 on every arm, every repeat**. So the bench_base clean-arm reading (`utility_mean` 0.2035, `final_answer_rate` 31.14%, `steps_mean` 11.5) measured the empty-observation harness, not the defender: with `observation: ""` the model has nothing to reason over, so it keeps calling tools until `BE_MAX_STEPS`. Do not diagnose termination or utility from bench_base again.
  **The real caveat is the opposite one, and it is not visible in ASR.** `judge.py` scores a rollout that never triggered the injection as `fail` = blocked = TP (`injection_visible_turn is None`, layer 2), and `Controller.run_replay` only substitutes the vendored observation when the agent calls the injection-bearing tool. Poison-delivery rate falls **81.8% → 73.0% → 48.4%** across the three arms (target-tool call rate 84.9% → 69.8% → 45.3% on repeat 1), so **more than half of r11's TPs are avoidance, not resistance**. Conditional on the payload actually reaching the context, ASR is **17.63% → 7.86% → 5.10%** — still a 3.5× improvement, but the headline 2.52% is inflated. Utility does *not* collapse on the undelivered half (attacked `utility_mean` 0.8239 overall), i.e. the defender routes around the poisoned tool and still finishes, which will not transfer to an injection placed in whatever tool it does call. **Always report `poison_delivered_rate` and `asr_given_delivered` alongside ASR** — `summarize_replay.py` prints both. Also note r11 > r5 here, the reverse of the training-round ranking, so pick the evaluated best round, not the metric-log best. `stepwise_eval.py` cannot produce any of this: it is one `agent.decide()` per record with no env and no loop.
- **The trajectory-level attempt (`last_traj`, K=2) DID fix GRPO saturation and did NOT improve held-out defence. Result: negative; do not repeat it.** (2026-08-23, 12 rounds completed, `configs/agentdojo_full_last_traj.yaml` = plan_abc + `grpo_traj_group_size: 2` + `grpo_max_prompts_per_round: 160` + `grpo_clean_prompt_ratio: 0.25`; `grpo_beta` deliberately left at 0.01 so attribution stays on the grouping.) Two findings, and they point opposite ways:
  * **The mechanism worked, measured on the trainer's own logs.** Trajectory pooling fired on 45–88 generation batches per round (400–760 completion slots re-based), every round. `frac_reward_zero_std` fell from plan_abc's **73.3%** to 20.5% (r1) rising to ~50% (r11, peak 63.5% at r8), and the reward **median never pinned at the +3.20 ceiling** (1.71 → 2.78, max 3.04) where plan_abc's median *was* exactly 3.2000. Entropy 0.5498 → 0.1079. So "one generation batch == one trajectory" plus the pooled-advantage fallback does restore gradient signal.
  * **The held-out replay says it bought nothing.** Same harness, 3 repeats, pooled over 159 attacked records: base 23/159 = 14.47% → `lt_r4` 11/159 = 6.92% → `lt_r11` 10/159 = **6.29%** → `plan_abc_r5` 9/159 = 5.66% → `plan_abc_r11` 4/159 = **2.52%**. f1: 0.8799 / 0.9337 / 0.9460 / 0.9434 / 0.9718. Fisher exact: `lt_r11` vs base **p=0.026** (real), vs `plan_abc_r5` **p=1.00** (identical), vs `plan_abc_r11` p=0.17 (nominally worse, not significant at n=159). `asr_given_delivered` is worse too (0.1086 vs 0.0510), so this is not a delivery artifact. Where `last_traj` IS better: it **engages** more (`poison_delivered_rate` 0.5786 vs 0.4843, i.e. less routing-around), attacked `utility_mean` 0.8415 (best of all six arms), `clean_final_answer_rate` **1.0000**; clean `utility_mean` 0.7667 is below plan_abc_r11's 0.8364. `false_alarm_rate`/`injection_flag_rate`/`refusal_rate` are 0.0000 on every arm and repeat, as before.
  * **The training-round metric log is again a bad selector.** `last_traj` training ASR bottomed at r5 (0.1135, f1 0.9314) and drifted back to 0.2426 by r11, yet on the held-out replay r11 ≥ r5 ≥ r4. Also note the attacker got measurably more *latent* this run (`delta_latent_share` 0.0059 → **0.1077**, vs 0.000–0.038 in plan_abc), so the rising training ASR is partly a harder adversary, not only defender drift. Conclusion for future work: reward-signal saturation was **not** the binding constraint on held-out ASR — spend effort on the ~50% of TPs that are avoidance rather than resistance, and on per-task forgetting, not on further group/advantage surgery.

## Vendored Training Frameworks

`evoguard/training/AEPO/verl_aepo_entropy/` (RL stack built on verl) and `evoguard/training/LLaMA-Factory/` (SFT/LoRA) vendor two complete third-party projects. Treat them as external dependencies — do not edit their contents directly. Our integration layer wraps them purely via subprocess shells generated by `grpo_runner.py` and `sft_runner.py`, emitting yaml/hydra overrides/dataset jsonl/shell commands in a way that supports `dry_run=True` inspection before actually firing GPU jobs. Their own requirements.txt/pyproject.toml hold the heavyweight ML dependencies pulled separately at the moment you flip `dry_run=False`.

**Dependency-conflict caveat**: both vendored trees were editable-installed via `pip install --no-deps -e ...` but their pinned deps (`numpy<2`, `peft<=0.15`, `trl<=0.9.6`, `transformers<=4.52.4`) CONFLICT with the installed runtime stack in this env (`numpy 2.x` / `peft 0.19` / `trl 0.19` / `transformers 5.x`). Do NOT rely on `llamafactory-cli` or `verl.trainer.main_ppo` at runtime — they will break. The **native-trainer path** (`native_runner.py` + `native_grpo_runner.py`) was added precisely to sidestep these — prefer it for new work.

There is no top-level build/install metadata for the EvoGuard package itself yet; runtime imports rely solely on PYTHONPATH being the repo root while dev work happens inside the conda env cloned from `/ssd1/conda_envs/stabletool`.
